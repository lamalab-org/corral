Annotation Guidelines

Your Task

You are reviewing LLM-generated annotations of scientific reasoning traces. For each node and edge the model extracted, decide whether it is correct or incorrect based on the trace messages shown in the left panel.

The goal is to judge the model’s work using the same narrow criteria the model was given. Do not apply richer human inference—annotate only what is explicitly stated. Because we are auditing one specific annotation pipeline rather than building a new one, your review should follow the operationalization described below, even when your own reading of the trace might differ.

Core Rule

Annotate explicit content only.

  • Do NOT invent hidden thoughts or implied steps.
  • Do NOT infer unstated motivations.
  • Do NOT add edges just because they seem logically plausible.
  • Do NOT recover missing reasoning from world knowledge.
  • Do NOT reward good reasoning unless it is verbalized in the trace.

Evidence Requirement

Every accepted node and edge must have at least one supporting quote that:

  • Comes from the trace (minor whitespace or formatting differences from the original are acceptable, since the annotation pipeline may normalize text)
  • Is tied to a specific message index
  • Is sufficient to justify the annotation under the rules below

A quote that clearly corresponds to the referenced message content should be accepted even if it is not character-for-character identical to the raw text (e.g., collapsed newlines, trimmed whitespace).

Node Types

HHypothesis — a candidate explanation, or a working assumption about the system. It should be a revisable claim, proposal, suggestion, or the current best guess about the answer. Information in task definitions or environment descriptions do not count as H. Partial or full reiteration of the task description does not count as H. Correcting a typo in a tool argument does not count as H.
TTest — any information-seeking action, including experiments, evaluations, or lookups. Both the intention and the concrete tool call qualify as T; what matters is that the system is seeking new scientific information to evaluate a hypothesis (H) or a judgment (J). If both the intention/plan and the actual tool call are present within the same message, count only the tool call as T. Every tool call (with the tag <action>) must be assigned as either T or N.
EEvidence — all Observation messages must be assigned with and only with an Evidence (E) node. Only Observation messages can be E, with the exception of the task description message.
JJudgment — an interpretation of test results (Observation) that goes beyond the literal repetition of the raw output. If the agent restates an observation while adding any evaluative, comparative, or inferential content—even brief—it is J.
NNeutral — for boilerplate operations like writing or copying files, or non-scientific tool calls. Only the tool calls (with the tag <action>) of a message can be assigned as N.
FFinal Answer — only the message that contains a final submission (with tag <final_answer>) must be assigned with an F node.
CCommitment (pseudo-node) — if from the actions of the agent it can be inferred that they have reached an implicit commitment to an answer that is not yet fully supported by evidence and they are refusing to revise it. The Final Answer (F) may also be C if it is not fully supported by evidence. Unlike other nodes, C does not require explicit text; it may be inferred from context.
HHypothesis — a candidate explanation, a working assumption about the system, or the current best state of a parameter or answer. This includes quantitative estimates, parameter choices, and proposed plans that the agent treats as revisable claims (e.g., “time per line should be ~0.4 s”, “the compound is X”). If the agent explicitly states a candidate value and later evaluates or revises it, it counts as H.
TTest — any information-seeking action: designing an experiment, calling a tool, executing code, querying documentation, or running a simulation. Both the abstract plan (“I will check X”) and the concrete action (“execute code to set parameters”) qualify as T; what matters is that the agent is seeking new information.
EEvidence — the result of any observation. This includes tool outputs, code execution results, retrieved documentation content, API responses, error messages, and any factual information the agent receives from the environment. If the trace shows that the agent received information from a tool or the environment, that information is E regardless of its format.
JJudgment — an interpretation of evidence that goes beyond literal repetition of the raw output. If the agent restates an observation while adding any evaluative, comparative, or inferential content—even brief (e.g., “this confirms…”, “consistent with…”, “this indicates…”)—it is J. Pure copy-paste of a tool output without any commentary remains E.
UUpdate — an explicit revision: replacing a hypothesis, abandoning a plan, changing a parameter value, or reranking candidates. There must be a clear before/after in the trace; merely proposing a new idea without reference to what changed is not U.
CCommitment — a final lock-in statement: “the answer is X”, “I conclude…”, a final submission. The agent must signal that it is done deliberating on this point.

Do not use V even if the text contains reliability appraisal. Fold reliability comments into J when they are explicitly interpretive.

Edge Relations

testsAllowed between H→T and J→T. H→T: the Test directly addresses the Hypothesis’ claim, or attempts to falsify or verify it. J→T: the Test is designed in response to the Judgment, or the Judgment motivates the test design.
observesAllowed only between T→E. The Evidence is the direct result of the Test.
informsAllowed between E→H, E→J, E→C, J→C, J→H, J→J. E→J: the Judgment is an interpretation of the Evidence. E→H / J→H: the Evidence or Judgment provides information relevant to the Hypothesis. E→C / J→C: the Commitment is informed by the Evidence or Judgment (not necessarily explicit). J→J: the later Judgment is a refinement or extension of one or more earlier Judgments.
updates_toAllowed only between H→H. The later Hypothesis is a revision of the earlier one, based on intervening nodes.
competes_withAllowed only between H→H. The two Hypotheses are alternative explanations directly compared or evaluated against each other, co-existing at the same time. If a hypothesis is introduced as a revision of the first, use updates_to instead.
contradictsAllowed between E→H and J→H. The Evidence or Judgment explicitly contradicts the claim of the Hypothesis.

Allowed directions

Only the directions listed above are permitted. Any combination not listed (e.g., T→H, E→T, H→J) is forbidden and should be marked incorrect.

testsA test evaluates a hypothesis, or a test produces evidence. Both H→T (“hypothesis drives the test”) and T→E (“test yields evidence”) are common patterns.
observesEvidence is observed as a direct product of a test or tool call. Typically T→E. Both tests and observes can link T to E: use tests when the emphasis is on the test evaluating something, and observes when the emphasis is on the evidence appearing as output.
usesOne node’s content functionally informs or supports another. The most common pattern is E→J (evidence supports a judgment), but uses applies broadly: evidence informing a test design (E→T), a judgment informing a hypothesis (J→H), evidence feeding into a commitment (E→C), etc. Accept uses whenever the source node’s content is clearly drawn upon in the destination node.
updates_toAn explicit transition: U moves from one H to another, or one state to a revised state.
competes_withBetween alternative hypotheses that the agent explicitly considers as rivals.
contradictsEvidence or a judgment explicitly contradicts or refutes a hypothesis.

Preferred directions

The canonical directions are H→T, T→E, E→J, E→U, U→H, E→H (for contradicts). However, the trace may justify other orientations (e.g., E→T for uses when evidence informs a follow-up test). Accept the direction used in the annotation if the support quote justifies the stated relationship.

Quick Decision Rules

  • If the node/edge has no corresponding content in the trace at all → incorrect
  • If the quote clearly does not match the referenced message → incorrect
  • If a message is an Observation but is not labeled E → incorrect
  • If a tool call (<action>) is neither T nor N → incorrect
  • If it is only a literal restatement with zero evaluative content → it is not judgment
  • If C is claimed but there is no evidence of an implicit refusal to revise → it is not commitment
  • If an edge direction or type is not in the allowed list → incorrect
  • If two items are merely adjacent in time with no functional link → no automatic edge
  • If the node/edge has no corresponding content in the trace at all → incorrect
  • If the quote clearly does not match the referenced message → incorrect
  • If it is only a plan and has no observational content → it is not evidence
  • If it is only a literal restatement with zero evaluative content → it is not judgment
  • If there is no explicit belief change → it is not an update
  • If there is no explicit lock-in → it is not commitment
  • If two items are merely adjacent in time with no functional link → no automatic edge

Workflow

  1. Read the messages in each window (left panel).
  2. Review the LLM-extracted nodes and edges (right panel).
  3. For each item, check whether the support quote exists in the referenced message and whether the assigned type/relation is consistent with the definitions above.
  4. Mark correct if the annotation is defensible under these definitions, or incorrect if it clearly violates them.
  5. Add notes for ambiguous or incorrect items.
  6. Navigate to the next window and repeat.
  7. Save your progress periodically.

Uncertainty Policy

When genuinely uncertain, consider whether the annotation is defensible under the definitions above before rejecting it. If the type or relation assignment is a reasonable reading of the trace—even if it is not the only possible reading—mark it as correct and optionally add a note. Reserve incorrect for cases where the annotation is clearly unsupported or misclassified. This approach reflects the conservative design of the pipeline: nodes and edges were only added when the model found explicit textual support, so the prior expectation is that most annotations have a basis in the trace.
